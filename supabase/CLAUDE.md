## Grants and RLS

- **Grants are explicit.** Default privileges are revoked, so a new table is reachable by no API role (not even `service_role`) until its migration grants exactly what each needs: `service_role` `select, insert, update, delete` (never `truncate`), `authenticated` only under RLS and often per column. `anon` gets nothing.
- **RLS on every table.** Policies read roles from the signed token via `private.has_role()` / `private.is_admin()` (admin + `aal2`), never by querying `roles` per row; wrap them as `(select private.…())` so they run once per statement. Tables without policies are server-only.
- Cross-table checks use `SECURITY DEFINER` helpers in `private` (no policy recursion); every `private` function sets `search_path = ''` and has execute revoked from `public`.
- Functions callable through the API are `security invoker` unless there's a written reason; `revoke all … from public, anon, authenticated, service_role` then grant exactly who may call them.

## Access model

- **Tenants first.** Every rule below applies inside the caller's tenant only: each tenant-owned table has a restrictive `Own tenant only` policy (`tenant_id = private.tenant_id()`, or `private.is_super_admin()` = `super_admin` + `aal2`). `private.is_admin()` is true for Super Admins too, so "admins with 2FA" means *of this tenant*, or a Super Admin anywhere. `tenants`: users read their own; Super Admins all; writes server-only.
- `profiles`, `roles`: users read their own; admins with 2FA read all. The token hook (`supabase_auth_admin`) reads both. Writes are server-only. An admin deactivates an account through `set_account_status` (secret key only; the actor must be an active admin of the account's agency or an active Super Admin, never their own account, and only an active Super Admin may deactivate an admin or Super Admin, as only they grant those roles — `IVA01`, `IVA14`; only `inactive` for now, as reactivation must respect the invited / VA-review rules). Until the app follow-up lands, the app still deactivates with a direct secret-key update, logged as System.
- `clients`: a client reads their own record, a VA those actively assigned to them, a Closer those they created (and creates and edits them), an admin with 2FA all. Status, activation and the login link are server-only (column grants). Conversion stores the agreed package and copies lead details into `business`. `registration_email_sent_at` (when the onboarding email was accepted by the mail provider), `consented_at` and `onboarding_submitted_at` are server-only; a Closer or admin may correct `billing`. `disabled_at` hides a client from the list without deleting the record. `onboarding_status` is the registration packet (`ready` through `invite_sent`); `client_packets` holds that packet's link, signature and payment file and is server-only. The time zone follows the client's country. `client_notes` is the append-only note list (`record_client_note`); admins read and insert their own rows. A note may include one file of up to 2 MB.
- Registration packet steps (20261029172015_registration_agreement; secret key only, security invoker): through the link's token hash the customer saves `save_client_packet_details`, `accept_client_agreement` and `save_client_payment_proof` one at a time. Each locks the client, then the packet (`private.lock_client_packet`), and is allowed while `pending_customer`, or in `changes_requested` only for a step still open; refusals as `submit_client_packet`'s (`IVA06` unknown link, `IVA09` disabled or not pending, `IVA08` not open or that step not sent back). Details and proof keep `submit_client_packet`'s checks. Saving a step removes its sent-back sections from `review_issues`; review sections are `basic | agreement | payment`, and rows stored with the old names count as `address`/`contacts` → `basic`, `package`/`consent` → `agreement` (`private.packet_section`). The admin's send-back (`save_client_review`, whose own list still accepts only the original names) stores Details, Agreement and Payment proof as `basic`, `consent` and `payment` (the app's `REVIEW_SECTION_FOR_STEP`), never `agreement`; the contract migration may widen `save_client_review` and store `agreement` instead. A step is open (`private.packet_open_sections`) while one of its sections is still marked, or it isn't complete: details missing a required field, no acceptance of the current terms (or no package to accept), no proof. Then `private.finish_client_packet` moves the packet to `pending_review` like `submit_client_packet` (also stamping `onboarding_submitted_at` and `consented_at`); each step returns the status afterwards. `submit_client_packet` still works for the old app. `client_agreements` is the acceptance evidence: version, the text shown, a terms snapshot built from the client row (`private.client_agreement_terms`: company, country, package, hours, term, monthly cents, start), the typed name, the contact email on file and the hashed IP. `accept_client_agreement` refuses while the package isn't set (`IVA45`; the country may still be empty) or when the terms the customer saw differ (`IVA43`), stores no new row when the packet's acceptance already has the same version, terms and name (a repeated submit), and otherwise sets the packet's `agreement_id` (and the consent fields current screens read); a details change that alters the terms clears `agreement_id`. Server-only (`service_role` select and insert; no policy for signed-in users), and append-only: a trigger refuses update, delete and truncate for everyone, the database owner included (`IVA44`). `client_packets.legacy_consent` marks packets signed with the earlier sample consent (in review, approved or invited when the migration ran). The five helpers (`packet_section`, `client_agreement_terms`, `packet_open_sections`, `lock_client_packet`, `finish_client_packet`) are security invoker and run with the caller's rights: `service_role` has usage on `private` and execute on these five (no other private function); signed-in users and visitors have none.
- `leads`: admins with 2FA read them, correct contact details and the `profile` jsonb, pause them (`disabled_at`), and delete one only while it is still `new` with no timeline and no meeting (`IVA05`). A Lead Gen reads the leads they own (`closer_id`); the select grant is still table-wide, so an owner can read `ip_hash` and `user_agent` too — column grants are planned with the lead handover (M8 slice 6). Inserts and spam metadata stay server-only. `convert_lead()` (security invoker, row lock, one transaction; refusals `IVA01`–`IVA03`) turns one into a client. `convert_lead_noted` also stores the confirmed package on that client (slug, hours, term, monthly cents, start date, time zone). Status flow, also in the app (`nextStatuses()`): open leads move freely, closed ones only reopen, converted ones are final — enforced by the `leads_guard_status` trigger (`IVA04`). `lead_events` is the append-only timeline (`record_lead_step`, `record_lead_call`, `convert_lead_noted`); admins read and insert their own rows, never update or delete them; a Lead Gen may author one only through `decide_discovery_call` (the rejection's junk remark). A call or a note may include one file of up to 2 MB.
- `employee_profiles` (renamed from `staff_profiles` in `rename_staff_to_employees`): employees (VA, Closer, admin) read and edit their own row, admins with 2FA everyone's. The address is one set of fields: street, additional info, city, state, postal code and country. Registration progress (`registration_status`, `invitation_sent_at`, `registration_completed_at`), the review (`review_status`, `returned_sections`, `return_note`) and the résumé bytes are server-only.
- `client_onboarding_links`: the onboarding form link a Closer sends a pending client. Only the token's SHA-256 is stored; links last 7 days, are single-use, one open per client, and are issued, revoked and used only by the server (`issue_onboarding_link`, `revoke_onboarding_link`, `submit_onboarding`, secret key only — each checks the actor is the client's Closer or an admin of its tenant). The Closer and admins with 2FA read link status, never `token_hash`; nobody else reads, and no signed-in user writes. Refusals `IVA06`–`IVA10`, `IVA13`, `IVA14`.
- `payments`: one row per payment, recorded by hand for now (`provider = manual`; Stripe in M4). An admin records it when confirming a registration packet: `accept_client_review_paid` (secret key only; the actor must be an active admin of the client's agency) approves the packet and stores the amount, `fee_cents` (bank or transfer fee, at most the amount), date and reference in one transaction; refusals `IVA14` (actor), `IVA21` (amount, fee or date), plus the review's `IVA06`/`IVA08`/`IVA09`. The sales summary totals paid payments: gross, fees, net = gross − fees. The client's Closer, the client (their own) and admins with 2FA read them; nobody else reads, and no signed-in user writes. `record_manual_payment` (the client's term, never a future date) and `void_payment` (only before activation) are secret key only, with the same actor check as onboarding links. A client with payments can't be deleted. `approve_client_payment` (20261029175327_payment_verification; secret key only, security invoker, same arguments and result as `accept_client_review_paid`) is what the app calls (slice 3), with the signed-in admin as the actor: it locks the client, then the packet, checks the actor the same way (`IVA14`; an active admin or Super Admin whose profile is in the client's agency — `recorded_by` must be in the payment's tenant), the amount, fee and date (`IVA21`), requires a bank reference (`IVA42`), needs the packet in review (`IVA06`/`IVA09`/`IVA08`) with an acceptance of the client's current terms, or `legacy_consent` only while the packet has no acceptance (`IVA43` — a Closer can still edit the terms during review), refuses a reference already on a paid payment in the agency (`IVA41`), and sets `app.actor` so the audit log names the admin. A paid reference is unique per agency, compared with whitespace removed and case ignored (hyphens count): `payments_paid_reference_key`, a partial unique index that also applies to the old functions (they get `23505`). The app no longer calls `accept_client_review_paid`, `accept_client_review` or `submit_client_packet`; a later contract migration drops (or revokes) all three: `accept_client_review(uuid)` (which still approves without a payment or acceptance check), `accept_client_review_paid` and `submit_client_packet`. `record_manual_payment` has no app caller but still meets the reference index, as a raw `23505`.
- Activation: `activate_client` (secret key only) needs the onboarding form submitted with consent, a `paid` payment, an enabled pending client and a fresh login (no roles, no client). In one transaction it moves the login into the client's tenant, grants `client` (assigned by the Closer or admin), links `user_id`, sets `active` and `activated_at`, and revokes open links. Refusals `IVA11` (form), `IVA12` (payment), `IVA15` (login already used).
- A client invited through the registration packet (`record_client_invite`, `onboarding_status = invite_sent`) becomes `active` with `activated_at` on the login's first sign-in (trigger on `profiles.signed_in_at`, `private.activate_client_on_sign_in`); a disabled client or one whose invite hasn't gone out stays pending.
- `client_va_assignments`: several active assignments per client, one active row per client and VA. A VA reads their own, a Closer those for clients they created, a client those for their own record; admins with 2FA read all and may end one (`status`, `ended_at`). Signed-in users cannot insert one (`IVA28`); the client's accept of a `va_shortlists` row does. `va_first_name` is a snapshot. `va_shortlists`: an admin with 2FA offers up to three open VAs (`IVA26` when the offer is not acceptable, `IVA27` when the row cannot change). The client accepts or declines their own offers while the company is active. Accept inserts the assignment. The VA reads their own rows. Admins may delete an `offered` row. The client reads a work profile of each VA on their own shortlist through `offered_va_profiles()` (security definer, signed-in clients only): skills, languages, education, certifications, past roles (position, company, dates), responsibilities, achievements and working hours, never personal details. `va_working_hours`: one half-hour window per weekday in Philippine time (`IVA29`). The open VA writes their own; admins with 2FA read them.
- `demo_slots`: 30-minute slots (on :00 or :30) a VA publishes for demo calls. A VA adds their own only while open (not deactivated, profile approved: `private.va_is_open`, the app's `vaPortalOpen`), in the future and at most 30 days ahead, and deletes one only while it is ahead and unused (a trigger refuses deleting a used slot for anyone, including a delete racing a booking). A VA reads their own, a client only the slots they may book now (`private.open_slot_ids`: 4 hours to 14 days ahead, an open VA, unused), an admin with 2FA all.
- `demo_bookings`: a client's demo call. One open (`pending` or `confirmed`) per client (the 1-call rule); a slot is used once, unless cancelled. Company, client time zone and VA first name are snapshots, so neither side reads the other's record. Written only by `book_demo` (the client's own active login; the client active and enabled, no active VA; settles stale bookings first), `decide_demo` (the booking's VA, still an open VA, while pending and ahead) and `cancel_demo` (the client's own active login, before it starts), secret key only. The client, the VA, the client's Closer and admins with 2FA read them. Refusals `IVA16` (has a VA), `IVA17` (open demo), `IVA18` (slot unavailable), `IVA19` (too soon or far), `IVA20` (can't change now).
- `discovery_times`: an admin's daily discovery-call times of day in PHT (+08:00, no DST, so a fixed shift), on :00 or :30, at most 6 per tenant (unique position 1–6). Admins with 2FA read them and replace them only through `set_discovery_times` (security invoker; it deletes only the caller's tenant's rows, because a Super Admin's policies pass in every tenant). Nobody else reads them.
- `meetings`: every call. `discovery` is a 30-minute call that belongs to a lead. The public form books one of the open slots through `request_discovery_call`, which sets the lead's profile source to Website (20261030163940_discovery_slot_source). The older form path, `submit_discovery_request` (the visitor's half hour in their country's time zone, so not always a UTC half hour), has no app caller since the slot picker; a cleanup migration drops it. `manual` is an admin booking: a title, start and end (at most 8 hours), optional client and employee, copied names, and the admin who created it. It starts `scheduled` and is cancelled rather than deleted (`create_manual_meeting`, `update_manual_meeting`, `cancel_manual_meeting`, `add_manual_meeting_note`, `update_manual_meeting_note`, `delete_manual_meeting_note`). Admins with 2FA read all; everyone on the invite lists (up to 20 clients and employees) can read it, and the first of each is also kept on `client_id` and `staff_id`. A Lead Gen still reads only the discovery calls they organise or decided. One open (`requested` or `scheduled`) discovery call per lead and one per tenant and start (partial unique indexes). A discovery call's organizer and decider must be Lead Gens; a manual booking's creator and history actor are admins (`enforce_role`). Discovery calls are written only by the functions below (secret key). A manual booking is written by its own functions (the signed-in admin). Neither is deleted. Closing, converting or pausing a lead expires its open request at once (`leads_settle_discovery`, security definer because an admin does it as `authenticated`); it runs while the lead is locked, so it skips (`SKIP LOCKED`) a request being decided at that moment rather than wait — that decision is then refused (`IVA23`) and the next request settles the leftover. Admins with 2FA read all; a Lead Gen reads the calls they organise or decided. Open requests reach Lead Gens only through `discovery_inbox()` — security definer, because the requests' leads have no owner yet: it checks in the database that the caller holds `closer` in their tenant and isn't deactivated, and returns the call and the lead's name, company, industry, country, package and message, never the email, profile, IP hash or user agent (the email reaches the Lead Gen when they confirm). It lists only future requests that the caller could still decide. A client books their own manual meetings from the client calendar (`create_client_meeting`, `update_client_meeting`, `cancel_client_meeting`, `complete_client_meeting`, `add_client_meeting_note`, 20261028093000_client_meetings; security definer like the admin functions, each checking the caller itself): only a signed-in request (API role `authenticated`) from an active `client` login whose company is active and enabled (`private.meeting_client`, else `42501`); the guests are always that company plus at least one VA on an active assignment to it (`IVA37`); a new or moved meeting starts ahead of now (`IVA38`). A client changes, completes, cancels and adds notes only to meetings they created (`created_by`, else `IVA01`); meetings an admin set up stay read-only for them, and only an admin edits or deletes a note. `created_by` may be an admin or a client.
- Discovery-call functions (secret key only; each checks the actor itself; the meeting row is locked before its lead): `open_discovery_slots` (security invoker; the default tenant's times, each day from today PHT, 12 hours to 14 days ahead, minus starts with an open call — the single source for the picker and the booking; a request left open on a closed, converted or paused lead doesn't count). `request_discovery_call` stores the lead, its meeting and the `requested` event in one transaction; it serialises per email and IP hash (advisory locks), first expires this visitor's (email or IP hash) unanswered requests whose time has passed, and any request still open on a closed, converted or paused lead, then refuses a start that isn't open (`IVA22`) and a second open request per email or a third per IP hash (`IVA24`); two at once on one start: the loser gets `23505`. `decide_discovery_call` (an active Lead Gen of the call's tenant, not someone else's lead — `IVA14`; a future request on an open, enabled lead — `IVA23`): confirming schedules it with the Lead Gen as organizer and makes them the lead's owner if it has none; rejecting needs a reason (1–300) and closes the lead with that reason as its junk remark. `record_discovery_outcome` (the call's organizer, still an active Lead Gen — `IVA14`; scheduled and started — `IVA23`): done or no-show; done moves a new, enabled lead to contacted. The two actor functions set the transaction-local `app.actor` to the actor, for the audit log.
- `audit_log`: who changed what, written only by the `*_audit` triggers (`private.write_audit`, security definer) on `leads`, `meetings`, `clients`, `client_va_assignments`, `tasks`, `va_shortlists`, `roles` (insert, update, delete) and `profiles` (status only). Each row: tenant, time, actor (user id, or system), action, record type and id, owning Lead Gen (`owner_id`: a lead's `closer_id`; a meeting's lead owner, else its organizer or decider; a client's creator; an assignment's client's creator; none for tasks and shortlists, which Lead Gens can't read, so their entries are for admins only, nor for roles and accounts), client, and `changes` — `{column: value}` on insert and delete, `{column: [old, new]}` on update, values only for the allow-list in `private.audit_allow` (statuses, ids, times, package terms; for tasks `client_id`, `va_id`, `status`, `deadline`, `deadline_timezone`, `done_at`, `closed_by`, `created_by`; for shortlists `client_id`, `va_id`, `status`, `offered_by`, `decided_at`) and `null` (name only) for everything else — a task's title and every name snapshot (`company_name`, `va_first_name`) included — so a new column is private by default. A client's shortlist accept is logged as the client, both the shortlist update and the assignment it inserts. Bookkeeping columns (`id`, `created_at`, `updated_at`, `tenant_id`, `leads.notified_at`, `profiles.signed_in_at`) never count as a change. No foreign keys, so an entry never blocks a write or the invite-rollback cascade; kept forever. Admins with 2FA read their agency's entries, a Lead Gen those they own (role from the token), nobody else — whether clients and VAs see entries for their own records (`docs/prd.md`) is decided with the activity screens (M8 slice 9); no API role writes, and a trigger refuses update, delete and truncate even for the secret key or a migration. Not audited: the timelines (`lead_events`, `meeting_events`, `client_notes`, `task_comments`, `client_agreements`), `discovery_times`, `va_working_hours`, payments (for now) and the demo tables.
- `meeting_events`: a meeting's append-only history (`requested`, `scheduled`, `rejected` with its reason, `done`, `no_show`, `note`, `expired`, and for a manual booking `updated` and `cancelled`); actor null only for `requested` and `expired`. A manual note may include one file of up to 2 MB, and stores the actor's name so the other person can read the history. The actor may be a Lead Gen (discovery), an admin (a manual booking) or the client who booked it. A trigger refuses update and delete for everyone, the database owner included, except a note on a meeting: an admin with two-factor can change its text or delete that note through `update_manual_meeting_note` and `delete_manual_meeting_note` (`IVA32` otherwise). Direct writes stay refused. The server only inserts every other row. Readable by whoever may read the meeting.
- VA bookings (20261030150000_va_bookings): a VA books from their calendar. `create_va_meeting` (security definer, an open VA signed in, else `42501`): with a client on their active assignment (`IVA46`) the manual meeting starts `requested` and waits for that client, who accepts (`scheduled`) or declines (`cancelled`) with `answer_va_meeting`; without a client it is a team call, `scheduled` at once, with optional staff guests. The VA cancels only meetings they created (`cancel_va_meeting`). A manual meeting's creator and history actor may now be a VA. A VA may also insert a task for a client on their active assignment (`created_by` = the VA); the client still reviews and closes it, and `guard_task` counts only the company's login as the client. `calendar_blocks` is time a VA set aside, on one of their own open tasks (`IVA47`) or as a titled to-do: owner and tenant come from the session (`fill_calendar_block`), only that VA and admins with 2FA read it, the VA deletes it, nobody updates it.
- `tasks`: a client creates work for the VA on their active assignment (company active and not disabled, VA portal open). Status (`guard_task`, 20261028021600_task_review): the VA starts (`todo` → `in_progress`) and submits for review (`todo`/`in_progress` → `review`); the client approves a review (`review` → `done`, shown as Closed), requests changes (`review` → `in_progress`), closes an open task without review (`todo`/`in_progress` → `done`, including after the assignment ends) and reopens a closed one (`done` → `in_progress`, which clears `done_at` and `closed_by`). Sending work back needs feedback, an active company and the VA still on the assignment. The VA never closes; nobody returns to `todo`. A move's note travels in `tasks.transition_note`, which the guard copies into `task_events` and clears (a check keeps the column empty). `task_events` is the activity (`started`, `submitted`, `changes_requested`, `approved`, `closed`, `reopened`, with the note, actor and actor's first name): written only by `guard_task` in the same statement as the move, readable by whoever can read the task, never updated, deleted only by the task's client when deleting the task (`guard_task_event`, `IVA25` otherwise). Until it is done, the client may change the title, description, deadline and deadline time while the company is active. A missing company timezone is snapshotted as Asia/Manila. No deadline time means the end of that day. The first move from `todo` to `in_progress` stamps `started_at`; a jump to `done` leaves it null, and nothing else may set it. The VA may advance status and comment only while that assignment is active and they are an open VA; they cannot change the title, description, deadline or deadline time. The client may delete their own task, which also removes its comments and files. The author of a comment may edit or delete that comment. Company name, VA first name and the deadline's IANA zone are snapshots written by trigger. `task_comments` is append-only. `va_messages` is an append-only note between that client and that VA (the author is one of those two, the assignment is active, the company is active). Admins with 2FA read tasks, comments and messages; Lead Gens have no access. Audited (see `audit_log`): ids, status and dates, never the title, the name snapshots or comments. The task timer and task duration (20261029063000_task_duration_timer) are removed again by 20261031142855_remove_task_timer: no `task_work_sessions`, `start_task_timer`, `pause_task_timer` or `tasks.duration_minutes`; VA hours are logged per client with timesheets (M14). Refusals `IVA22`–`IVA25` (the same numbers as discovery calls, mapped only by the task triggers) and `IVA35` for a message that cannot change or whose author is neither the client nor the VA.

## Conventions

- snake_case, plural tables, `_at` timestamps; uuid ids; user references point at `profiles(id)` (= `auth.uid()`).
- Enums for statuses, one status column per thing (no `is_active` beside a status).
- Restrict foreign keys keep deactivated users' and clients' history resolvable (`deleteAuthUser` only rolls back a failed invite).
- A column naming a user is role-checked by `private.enforce_role` (e.g. `clients.created_by` must be a Closer or admin — a Super Admin counts as an admin — `va_id` a VA), and a role can't be removed while something depends on it (`guard_role_removal`). Who may grant a role is checked from `assigned_by` (`guard_role_grant`): only a Super Admin grants `admin` / `super_admin`; an admin grants roles in their own tenant; an active Closer grants only `client`, in their own tenant; no `assigned_by` = a person at the database.
- **A new tenant-owned table** gets: `tenant_id uuid not null`; the `<table>_assign_tenant` trigger (inherit from the parent row; extend `private.assign_tenant()`); composite foreign keys `(col, tenant_id) → parent (id, tenant_id)` so it can't point across tenants; the `Own tenant only` restrictive policy; and `tenant_id` in no `authenticated` insert or update grant. A migration that redefines `private.assign_tenant()` keeps every existing case (a test fails if a table using the trigger has none). Exception: `client_agreements` has no trigger — its only writer, `accept_client_agreement`, sets `tenant_id` from the locked client and the composite foreign key enforces it, so that migration needn't redefine a function whose live version differs from the files.
- **Signed in or server**, in a trigger or function that treats them differently: decide by the request's API role, `current_setting('role', true) = 'authenticated'` (it keeps its value inside security-definer functions), never by `auth.uid() is not null` — `request.jwt.claims` is a setting any direct session can write. `service_role`, a direct session or any other role is the server; `auth.uid()` names the user only when the role is `authenticated`. A transaction-local flag that lets one inner write through is cleared right after that write (`guard_shortlist`).
- Invariants as constraints (`CHECK`, unique, FKs), mirroring the limits in each feature's `contract.ts`.
- Index foreign keys, RLS columns and list sort orders.
- Money in cents with a currency (M4). Secrets such as invite tokens stored only as SHA-256 (M3).
- Custom errors use their own SQLSTATE (`IVA01`…) so the app can map them to messages (see Error codes).
- **Audit actor** (`private.audit_actor`), by how the write arrived — `current_setting('role')`, the request's API role, which keeps its value inside security-definer functions and triggers:
  1. `authenticated`: `auth.uid()`; `app.actor` is ignored (a user can't name someone else). `anon` is system.
  2. `service_role` (the secret key): `app.actor` if set, else the row's own "by" column on insert (`roles.assigned_by`, `client_va_assignments.assigned_by`, `clients.created_by`, `tasks.created_by`, `va_shortlists.offered_by`), else system.
  3. Any other session (migrations, the SQL editor, Supabase Auth's own role): the same as `service_role`, and **never** `auth.uid()` — `request.jwt.claims` is a setting anyone in that session can write. The SQL editor's "impersonate user" runs as `authenticated` with that user's token, so its writes are logged as the impersonated user.

  An `app.actor` that isn't a uuid, or names someone outside the row's agency who isn't an active Super Admin, refuses the write. Only service_role-only functions call `set_config('app.actor', actor, true)` — always transaction-local (`true`), after their own actor check — so it can't leak into the next request. Attribution trusts our server: a leaked secret key could misattribute a write, but can't write or change `audit_log`.
- **A new audited table:** add it to `audit_log.record_type`'s check, an allow-list case in `private.audit_allow` (or none: names only), an owner case in `private.write_audit` (a missing one refuses the write; a test checks every `*_audit` trigger has both), any bookkeeping columns in `private.audit_ignore`, and its `<table>_audit` AFTER trigger. A secret-key write path that should show a person passes the actor to a function that sets `app.actor`.
- **Showing entries** (M8 slice 9): `actor_kind = system` is labelled "System" — never "Visitor" or a guess — and an unknown id shows as unknown.
