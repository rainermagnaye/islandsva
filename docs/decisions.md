# Decisions

Architecture decisions and why they were made. Change one by PR, updating the rule in `CLAUDE.md` (or the folder `CLAUDE.md`) that it explains.

| Decision | Why | Revisit |
|---|---|---|
| Server Actions for in-app mutations, Route Handlers for HTTP APIs | Actions update the UI in one round trip; routes give stable URLs for webhooks, external callers and rate limits | — |
| Zod for validation, server-side only (pinned `4.6.5`) | Less code than hand-written checks as M2–M7 add inputs; types inferred | — |
| `ApiResponse<T>` via `ok()` / `fail()` | One response shape for every endpoint | — |
| `@supabase/ssr` + `supabase-js` on the server only; CLI migrations in `supabase/` | Auth sessions and typed queries; versioned schema; browser bundle unchanged | — |
| Roles in the access token (custom access token hook) | Role checks read the token — no database query per request | If roles must apply instantly (sign the user out on change) |
| Admin two-factor enforced in the app and in RLS | Admins see every client's data | — |
| Multi-tenancy prepared, one tenant: `tenant_id` on every tenant-owned row, in the token, one restrictive RLS policy per table, composite foreign keys; Super Admin (2FA) across tenants; one tenant per user | Adding a second agency later is a data change, not a rewrite; existing per-role policies stay as they are | When a second tenant arrives: tenant per contact form and invite, Super Admin screens; memberships if a user needs several tenants |
| PGlite for database tests | Real Postgres without Docker; runs in CI | If tests need Supabase services beyond Postgres |
| Static CSP without nonces | Keeps public pages static | Portal pages, if a script-injection risk appears there |
| Theme follows the OS, no toggle | No script or cookie; public pages stay static | — |
| Demo scheduling: VA-published fixed 30-minute slots, pooled per tenant, in the app (no calendar sync); the client picks a time, not a person; 1-call rule = one open demo per client (partial unique index); stale bookings settled at the next booking, no cron | The smallest scheduler that enforces the rule in the database; no scheduled job or extra service | When VAs need recurring availability, reminders, no-show handling or external calendars |
| Rate limiting in Vercel Firewall | No extra service | When per-user limits are needed |
| `features/` + shared `lib/` | Each business area in one place as the app grows | — |
| Invite-only accounts; deactivate, never delete | B2B: employees are invited, Closers create clients; restrict foreign keys keep history resolvable | — |
| Résumé bytes in Postgres (`bytea`, ≤ 2 MB), not Storage | One store and one access model while files are rare and small | When files grow in number or size, or need download links |
| Documentation: root `CLAUDE.md` (everyday rules and map), `supabase/CLAUDE.md` and `components/CLAUDE.md` (database and UI, loaded only there), `docs/` (product, MVP plan, technical spec, runbooks, decisions) | Rules needed in most tasks stay always-loaded; the database and UI are separate workflows; runbooks and history aren't instructions. Fewer files, less drift | If another area grows its own workflow (e.g. payments in M4) |
| Discovery calls: admin-set daily times in PHT, every day, at most 6 a day agency-wide; the visitor books on the contact form; the Lead Gen who confirms owns the lead | One pipeline, one owner; no scheduling back-and-forth; the cap is a database constraint, not a check in code | If the agency needs per-Lead-Gen capacity or round-robin assignment |
| One `meetings` model for every call (discovery, intro, client↔VA), each a Google Calendar event with Meet on the organizer's own Google account (personal Gmail allowed, so an External OAuth app verified for production); only employees connect Google; free times = working hours minus Google free/busy; history in `meeting_events`; Google called over REST (no SDK) | One integration, one history and one set of rules for every call; clients need no Google account; no budget for Workspace seats; no extra dependency | If employees move to agency Workspace accounts (Internal app, no verification) or another provider is needed |
| VA Match replaces the client↔VA demo: the admin shortlists 1–3 VAs, the client accepts one or requests an intro call first (the VA confirms); `demo_slots` / `demo_bookings` give way to `meetings` | The client chooses their VA instead of the admin guessing; no second scheduler | — |
| Meetings between an active client and their assigned VAs have no approval step: either side schedules, and the event and Meet link are created at once; open-ended length; clients pick from the VA's working hours minus Google busy times; the status (scheduled, done, no-show, cancelled) and its history are what's tracked. Calls before that relationship keep a confirm: discovery (Lead Gen) and intro (VA) | They already work together, so fewer steps; the status shows what happened. A discovery confirm assigns the lead's owner; an intro call comes before the VA has agreed to the client | If VAs get booked at times they can't make, add a VA confirm step |
| No VA time tracking in the MVP; performance comes from tasks (done, on-time rate, overdue) | Smallest useful measure; hours vs package follows with time tracking | When clients need hours worked |
| Task deadline is a calendar date in the client's IANA timezone, snapshotted on the task; on-time and overdue are computed, never stored | A deadline is a day in the client's country zone; the snapshot keeps a later timezone correction from moving the bar | If a task needs a time of day |
| The client accept is the only app path that creates an assignment. An admin offers 1–3 VAs and may end one assignment. Working hours are weekly half-hour windows in Asia/Manila. Demo tables stay until an intro call can be booked | The shortlist is the source of truth. Several VAs can be active. Intro calls need meetings and Google, which are not built yet | If an intro needs a length other than 30 minutes, or an admin must assign when the client cannot sign in |
| Audit log: one append-only `audit_log` table written by database triggers, from M8 (built in slice 2, covering tasks and VA shortlists too); Lead Gens see entries for their own leads, calls, clients and assignments; task and shortlist entries have no owner (Lead Gens can't read those tables), so only admins see them; admins see all; clients and VAs decided in slice 9; no PII or free text in it | Nothing that changes a row can skip it (app, admin, Google sync); one place for who-did-what, separate from the readable timelines | If entries must be kept outside the database or exported for compliance |
| Discovery calls in the database (M8): fixed 30-minute slots on :00 / :30 at admin-set PHT times, as a fixed +8 h shift (Manila has no DST; PGlite needs no time-zone data); bookable 12 hours to 14 days ahead; one function (`open_discovery_slots`) is the source for both the picker and the booking; the Lead Gen who confirms owns the lead (`leads.closer_id`, no new `owner_id`); a rejection needs a reason and closes the lead as junk; stale requests expire at the next request, no cron | Rules live in constraints and one transaction, so the list and the booking can't disagree; reusing `closer_id` keeps one owner column | If Manila adopts DST, or the agency needs a different window or per-Lead-Gen capacity |
| The Lead Gens' discovery inbox hides the visitor's email (and IP hash, user agent, profile) until a Lead Gen confirms; it is a `SECURITY DEFINER` function that checks the caller's role and status in the database, not a leads policy | Unowned leads stay unreadable to Lead Gens; an inbox needs only what's required to decide; a deactivated Lead Gen's token keeps its role for up to an hour, so the token alone isn't trusted | If Lead Gens need to contact a visitor before confirming |
| Slot squatting: at most one open discovery request per email and two per IP hash, serialised with advisory locks; both refusals share one code (`IVA24`) and a generic message | Stops one visitor from holding every slot; a generic message reveals nothing about other requests | If shared office IPs hit the cap, or abuse moves to many IPs (Firewall rate limit) |
| VA load is the sum of `hours_per_week` on each active, enabled client that VA is actively assigned to; co-assigned VAs each show the full week. Contracted revenue stays `recurringRevenue()` and is never derived from those hours | A shared VA still covers that client's whole week; the Sales page is the only revenue figure | If an assignment gains its own hour split |
| Discovery-call visitor emails: an acknowledgement when the request is stored, a confirmation when a Lead Gen confirms, and an "expired, pick another time" email when nobody confirms in time; all fixed text plus the call time, never anything the visitor typed; none on reject | The visitor needs to know the request arrived and its outcome (product decision); fixed content keeps the form from being used to send our mail with someone else's words, and the honeypot, Turnstile, per-email and per-IP request caps, a Firewall rate limit, at most 1 acknowledgement per address a day (3 per 30 days) and 40 automatic visitor emails per agency a day bound the volume, so a flood can't use up the shared Resend allowance | If abuse shows in Resend bounces or complaints (then double opt-in: a confirm-your-request link), or when Google's invite replaces the confirmation (M9) |
| A discovery request can be confirmed until 2 hours before its start, then expires; Supabase `pg_cron` expires them every 15 minutes and calls a signed internal endpoint (production only) that sends the expiry emails | The visitor hears in time to pick another slot; one scheduler that runs often enough, with the Resend key only in the app | Vercel cron (Hobby: once a day), a Supabase Edge Function (second runtime and key home) and Resend from `pg_net` (key in the database) were rejected; revisit on Vercel Pro or if a queue is added |
| A discovery request isn't a lead until a Lead Gen confirms it: same `leads` row, but lists, counts and search leave out unowned leads that came from a discovery request and were never confirmed (open, expired or rejected) | No second table or copying contact fields on confirm; slice 1's functions stay as built | If requests need their own fields or retention |
| Audit actor = how the write arrived: a signed-in user is `auth.uid()` (they can't name anyone else); the secret key or a direct session is the transaction-local `app.actor` set by a service_role-only function (checked: a user of the row's agency or a Super Admin), else the row's own "by" column on insert, else System. A direct session's token is never trusted | `request.jwt.claims` is a setting any direct session can write; the API role survives into security-definer triggers, so the rule holds through nested triggers. Attribution trusts our server: a leaked secret key could misattribute, but can't write or edit `audit_log` | If writes arrive another way (Edge Functions, Google sync in M9) |
| Audit values: default deny — only allow-listed columns (statuses, ids, times, package terms) keep values; everything else, and every new column, is recorded by name; no foreign keys from `audit_log`; kept forever; visitors and unattributed writes are labelled "System" | No PII or free text in the log by construction; an audit row can never block a write, delete or rollback | If compliance needs exports, retention limits or values for more columns |
| Deactivating an account goes through `set_account_status` (secret key, actor checked like a role grant) instead of a direct update | The audit log shows which admin did it, and the database — not just the app — refuses a cross-agency or self deactivation; only a Super Admin deactivates an admin or Super Admin (as only they grant those roles), so a tenant admin can't lock out the others | When reactivation is offered (it must respect the invited / VA-review rules) |
